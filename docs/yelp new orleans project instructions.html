Project overview

In this project, you will use the Yelp Open Dataset to investigate restaurants in the New Orleans area. You will work with several large JSON databases rather than a single, already-cleaned table. Your analysis should demonstrate that you can import, clean, connect, summarize, visualize, and explain real-world data.

The final product should be an employer-facing data product in a GitHub repository. The main report may be written directly in README.md, or it may be a rendered HTML report linked from the README. In either case, a potential employer should be able to understand your question, view your tables, graphs, and maps, follow your data workflow, and inspect the source code.

The data

Download the Yelp Open Dataset from the official Yelp Open Dataset page. The files used in this project are JSON databases stored as one JSON record per line:

Step 1: Import the large JSON files

The Yelp files are much larger than the small CSV files used in ordinary examples. jsonlite::stream_in() is useful because it reads a JSON stream rather than requiring you to write a complicated parser by hand.

Place the downloaded files in data/raw/. The following code imports the business table and keeps the columns needed for this project.

Code 
business_file <- "data/raw/yelp_academic_dataset_business.json"
review_file <- "data/raw/yelp_academic_dataset_review.json"

business_raw <- jsonlite::stream_in(
  file(business_file),
  verbose = FALSE
)

business <- business_raw |>
  select(
    business_id, name, address, city, state, postal_code,
    latitude, longitude, stars, review_count, categories
  )

review_raw <- jsonlite::stream_in(
  file(review_file),
  verbose = FALSE
)

reviews <- review_raw |>
  select(business_id, user_id, stars, date, text, useful, funny, cool)

Step 2: Clean and filter to New Orleans restaurants

The business file contains many types of businesses and many cities. You must show how you identify restaurants in the New Orleans area. Do not assume that every business in the file is a restaurant.

Begin by examining the relevant fields:

Code

Create a restaurant subset. Yelp’s categories field contains comma-separated category labels, so use a text pattern rather than exact equality.

Code 
new_orleans_restaurants <- business |>
  filter(
    state == "LA",
    city == "New Orleans",
    !is.na(categories),
    str_detect(categories, regex("Restaurants", ignore_case = TRUE))
  ) |>
  mutate(
    postal_code = na_if(postal_code, ""),
    categories = str_squish(categories),
    business_name = str_squish(name)
  ) |>
  distinct(business_id, .keep_all = TRUE)

new_orleans_restaurants |>
  summarise(
    number_of_restaurants = n(),
    missing_latitude = sum(is.na(latitude)),
    missing_longitude = sum(is.na(longitude)),
    missing_categories = sum(is.na(categories))
  )

Step 5: Add an official geographic boundary with a spatial join

A latitude and longitude pair is a point. A city boundary is a polygon. A spatial join connects a point to the polygon that contains it.

Here, you will download Louisiana place boundaries from the U.S. Census TIGER/Line data using tigris. The Yelp city field is a text label; the spatial join gives you a second, independently constructed geographic label.

Code 
louisiana_places <- tigris::places(
  state = "LA",
  cb = TRUE,
  year = 2024,
  class = "sf"
)

restaurant_points <- new_orleans_restaurants |>
  filter(!is.na(longitude), !is.na(latitude)) |>
  st_as_sf(
    coords = c("longitude", "latitude"),
    crs = 4326,
    remove = FALSE
  )

restaurants_with_place <- restaurant_points |>
  st_join(
    louisiana_places |>
      select(GEOID, place_name = NAME),
    join = st_within,
    left = TRUE
  )

restaurants_with_place |>
  st_drop_geometry() |>
  count(city, place_name, sort = TRUE)

Compare city with place_name. Investigate mismatches rather than automatically deleting them. Possible explanations include geocoding differences, businesses near a boundary, postal-city labels, or coordinates that need checking.

Step 6: Choose and defend a geographic area

Do not assume that one geographic system is automatically the best way to divide New Orleans. Different boundaries answer different questions. Your job is to investigate several possibilities, perform preliminary analyses, and then defend the geographic area that best fits your research question.

You must compare at least two of the following geographic systems. You may compare more than two if your computer and research question make that practical:

  • ZIP Code Tabulation Areas (ZCTAs): Census approximations of ZIP-code areas. These are useful for postal and business-location questions, but they should not automatically be described as neighborhoods.
  • Census tracts: Statistical areas designed for population and demographic analysis.
  • Census block groups: Smaller statistical areas within census tracts. They provide more detail, but they may contain too few restaurants for stable comparisons.
  • Neighborhood Statistical Areas: New Orleans-specific local boundaries created for planning and community analysis.
  • Wards: Historical or administrative divisions of New Orleans that may be useful for civic or historical questions.

You should obtain boundary data from an appropriate source. Census geographies can be obtained through tigris; New Orleans-specific layers such as Neighborhood Statistical Areas and wards can be obtained from the City of New Orleans or Data.NOLA.gov.

Geographic comparison requirements

For each geographic system you test:

  1. Convert the Yelp latitude and longitude values into an sf point object.
  2. Use a spatial join to assign each restaurant to an area.
  3. Count the number of restaurants in each area.
  4. Calculate the average business rating and, if possible, the reviewer-adjusted rating.
  5. Check how many restaurants are unmatched or assigned to NA.
  6. Identify areas with very few restaurants and explain how that affects your conclusions.
  7. Create at least one map or comparison plot.

Select reviewers with enough activity

Reviewers with only one review cannot provide much evidence about their usual scoring behavior. Count reviews within your selected category group and define a minimum activity threshold. Five reviews is a reasonable starting point, but you may choose a different threshold if you justify it.

Code 
reviewer_activity <- category_reviews |>
  count(user_id, name = "reviews_in_selected_categories") |>
  arrange(desc(reviews_in_selected_categories))

eligible_reviewers <- reviewer_activity |>
  filter(reviews_in_selected_categories >= 5)

selected_reviewer_reviews <- category_reviews |>
  semi_join(eligible_reviewers, by = "user_id")

Report how many reviewers were retained and what percentage of category reviews they represent. Explain how changing the threshold changes the results.

Normalize each reviewer’s scores

Some reviewers may give almost every restaurant five stars, while others may rarely give five stars. Create a reviewer baseline using the reviewer’s mean and median score within the selected category group. Then subtract the baseline from each reviewer’s individual rating.

For example, if a reviewer has an average score of 5 and gives a restaurant 5 stars, the normalized score is 5 - 5 = 0. If that reviewer gives a restaurant 4 stars, the normalized score is -1. A reviewer whose usual average is 3 and who gives a restaurant 4 stars has a normalized score of +1.

Code 
reviewer_baselines <- category_reviews |>
  group_by(user_id) |>
  summarise(
    reviewer_mean = mean(stars, na.rm = TRUE),
    reviewer_median = median(stars, na.rm = TRUE),
    reviewer_review_count = n(),
    .groups = "drop"
  )

category_reviews_adjusted <- category_reviews |>
  left_join(reviewer_baselines, by = "user_id") |>
  mutate(
    normalized_mean_score = stars - reviewer_mean,
    normalized_median_score = stars - reviewer_median
  )

eligible_adjusted_reviews <- category_reviews_adjusted |>
  semi_join(eligible_reviewers, by = "user_id")

Use the mean- or median-based score as your primary normalized score and explain your choice. Do not describe the normalized score as a new Yelp rating. It measures whether a reviewer’s rating was higher or lower than that reviewer’s usual rating behavior.

Compare raw and reviewer-adjusted results

Create a restaurant-level table containing both the ordinary result using all reviewers and the reviewer-adjusted result using eligible reviewers.

Code 
restaurant_summary <- selected_restaurants |>
  select(business_id, business_name) |>
  left_join(all_reviewer_summary, by = "business_id") |>
  left_join(
    eligible_adjusted_reviews |>
      group_by(business_id) |>
      summarise(
        number_of_reviews_eligible_reviewers = n(),
        average_stars_eligible_reviewers = mean(stars, na.rm = TRUE),
        average_normalized_score = mean(
          normalized_mean_score,
          na.rm = TRUE

        median_normalized_score = median(
          normalized_mean_score,
          na.rm = TRUE
        ),
        .groups = "drop"
      ),
    by = "business_id"
  ) |>
  arrange(desc(average_normalized_score))

restaurant_summary |>
  filter(number_of_reviews_eligible_reviewers >= 5) |>
  slice_head(n = 10)

## Step 5: Add an official geographic boundary with a spatial join

A latitude and longitude pair is a point. A city boundary is a polygon. A spatial join connects a point to the polygon that contains it.

Here, you will download Louisiana place boundaries from the U.S. Census TIGER/Line data using `tigris`. The Yelp `city` field is a text label; the spatial join gives you a second, independently constructed geographic label.

```{r}

  state = "LA",
  cb = TRUE,
  year = 2024,
  class = "sf"
)

restaurant_points <- new_orleans_restaurants |>
  filter(!is.na(longitude), !is.na(latitude)) |>
  st_as_sf(
    coords = c("longitude", "latitude"),
    crs = 4326,
    remove = FALSE
  )

restaurants_with_place <- restaurant_points |>
  st_join(
    louisiana_places |>
      select(GEOID, place_name = NAME),
    join = st_within,
    left = TRUE
  )

restaurants_with_place |>
  st_drop_geometry() |>
  count(city, place_name, sort = TRUE)
```

### Normalize each reviewer's scores

Some reviewers may give almost every restaurant five stars, while others may rarely give five stars. Create a reviewer baseline using the reviewer's mean and median score within the selected category group. Then subtract the baseline from each reviewer's individual rating.

For example, if a reviewer has an average score of 5 and gives a restaurant 5 stars, the normalized score is `5 - 5 = 0`. If that reviewer gives a restaurant 4 stars, the normalized score is `-1`. A reviewer whose usual average is 3 and who gives a restaurant 4 stars has a normalized score of `+1`.

```{r}
#| eval: false

reviewer_baselines <- category_reviews |>
  group_by(user_id) |>
  summarise(
    reviewer_mean = mean(stars, na.rm = TRUE),
    reviewer_median = median(stars, na.rm = TRUE),
    reviewer_review_count = n(),
    .groups = "drop"
  )

category_reviews_adjusted <- category_reviews |>
  left_join(reviewer_baselines, by = "user_id") |>
  mutate(
    normalized_mean_score = stars - reviewer_mean,
    normalized_median_score = stars - reviewer_median
  )

eligible_adjusted_reviews <- category_reviews_adjusted |>
  semi_join(eligible_reviewers, by = "user_id")
```

Use the mean- or median-based score as your primary normalized score and explain your choice. Do not describe the normalized score as a new Yelp rating. It measures whether a reviewer's rating was higher or lower than that reviewer's usual rating behavior.
